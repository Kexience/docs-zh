# 参与贡献

- 在 [GitHub](https://github.com/testcontainers/testcontainers-java) 上给项目加个星，顺手帮忙宣传一下 :)
- 加入我们的 [Slack 工作区](http://slack.testcontainers.org)
- 如果你有想法、发现了可能的 bug 或者有其他疑问，可以[发起讨论](https://github.com/testcontainers/testcontainers-java/discussions)。
- 通过 [Pull Request](https://github.com/testcontainers/testcontainers-java/pulls) 提交改进或修复。如果你打算参与贡献，谢谢你！请务必做到：
  - 在动手做较大的改动之前先与作者沟通。
  - 遵循项目其余部分的风格、命名和结构约定。
  - 让每个提交保持原子性，便于合并。
  - 更新文档时，请参阅[我们的文档贡献指南](../contributing_docs/index.md)。
  - 运行 `./gradlew spotlessApply` 应用格式化（这需要你的机器上安装了 [Node.js](https://nodejs.org/)，装一个[包管理器](https://nodejs.org/en/download/package-manager/)会方便些）
  - 确认所有测试都能通过。可以运行 `./gradlew check` 来构建项目。**注意：** Gradle 的构建缓存（Build Cache）默认是开启的，但你可以加上 `--no-build-cache` 参数来禁用它。

## 贡献新的模块

我们经常收到关于新模块的提案（或者已经成型的 PR）。我们非常欢迎贡献，但新模块需要格外谨慎地对待。我们希望兼顾以下方面：

- 模块的实用性。
- 我们未来继续支持该模块的能力，尤其是在贡献者已经离开之后。
- 贡献者的时间，以免有人白费力气。

### 它需要是一个模块吗？

*注意：这份清单并不完美——在开始贡献模块之前，请务必先联系我们！*

- 该模块能让 Testcontainers 与某项流行或快速发展的技术搭配使用吗？
- 除了给出一段 `GenericContainer` 代码片段/示例外，该模块是否还能带来额外价值？例如：
  - 它是否把"在容器中运行程序"这一困难问题封装得很干净？
  - 它是否提供了针对该技术的[等待策略](../features/startup_and_waits/index.md)？
  - 它是否让客户端库的使用变得简单直接？

如果以上问题的答案都是肯定的，那么新建一个模块可能是个好方案。

否则，你完全可以：

- 发布一段代码片段
- 向 Testcontainers 仓库贡献一个示例
- 发布你自己的第三方库

无论哪种情况，都请联系我们，帮你验证方案！

### 检查清单

*建议：把这份清单复制粘贴到新模块的 PR 中。*

清单中的每一项都需要 Testcontainers 核心维护者来判断。有时可以例外；带 `should` 的条目比带 `must` 的条目更有可能协商通融。

#### 默认 Docker 镜像

- [ ] 应该是 Docker Hub 官方镜像，或者由信誉良好的来源发布（最好是该技术的官方支持公司或组织）
- [ ] 应该有一个可验证的开源 Dockerfile，并且有查看变更历史的方式
- [ ] 必须体现容器镜像打标签的通用最佳实践——例如，我们不使用 `latest` 标签，也不使用未来可能被改写的标签
- [ ] 必须让 Testcontainers 开发者和用户可以合法地拉取和使用。虽然存在用于表示接受 EULA 的机制，但无需许可即可使用的镜像更受青睐。

#### 模块依赖

- [ ] 模块应当尽可能少地使用依赖，
- [ ] 对于库，要么：
  - 如果它们很可能已经出现在用户测试的 classpath 上（例如客户端库或驱动程序），则应使用 `compileOnly`
  - 如果它们极不可能与用户的依赖发生冲突，则可以使用 `implementation`（从而成为传递依赖）。
- [ ] 如果使用客户端库来测试或使用该模块，这些库必须可以被 Testcontainers 开发者和用户合法地下载和使用。

#### API（例如 `MyModuleContainer` 类）

- [ ] 倾向于让默认行为就是正确的、最不令人意外的
- [ ] 确保方法名和参数名容易理解。很多用户不会看文档，因此基于 IDE 的替代手段（自动补全和 Javadoc）应当直观易懂。
- [ ] 模块的公开 API 只应处理标准 JDK 数据类型，绝不能暴露来自 `compileOnly` 依赖的数据类型。这样可以降低与第三方库未来版本出现兼容性问题的风险。

#### 文档

- [ ] 每个模块都必须有一个专门的文档页面，其中包含：
  - [ ] 总体概述
  - [ ] 使用示例
  - [ ] 视情况提供基本的 API 文档或进一步的使用指南
  - [ ] 依赖信息
  - [ ] 致谢（视情况而定）
- [ ] 考虑到很多用户不会阅读文档页面——即使最初把它加入项目的人读了，将来阅读/维护代码的人也未必会读。尽量避免出现只能从文档中获取的关键知识。

### 孵化中的模块

我们有一项策略，把新模块标记为"孵化中"，以便在更长一段时间内评估其可维护性和易用性。我们目前认为 3 个月是一个合理的期限，但也可能调整。

新模块应在其文档页面顶部加上以下警告：

> **注意**
>
> 本模块处于孵化中状态。虽然在当前版本的 Testcontainers 中它已经可以正常使用，但未来它可能会引入破坏性变更。有关我们孵化模块政策的更多信息，请参阅[我们的贡献指南](./index.md#incubating-modules)。

我们会定期评估孵化中的模块，并在适当的时候去掉这个标记。

## 审查 Dependabot PR

Dependabot 每周一检查更新，有可用更新时会将它们分成两个独立的 pull request：

- 通过 Gradle 管理的 Java 依赖和构建插件。
- 在 workflows 和 composite actions 中使用的 GitHub Actions。

常规版本更新在发布后有七天的冷却期。安全更新单独处理，不受该冷却期影响。`.github/dependabot.yml` 中已有的忽略规则会排除项目尚未准备好采用的升级。

在合并任何一个分组 pull request 之前：

1. 审查完整的 diff，确认其中每一项更新都在预期之内。
2. 确认相关的 CI 检查已运行并通过。对于 Java 依赖或构建插件更新，检查 CI 是否发现了覆盖受影响模块和示例的非空测试矩阵，以及相关的冒烟测试和文档检查是否已运行。
3. 逐项排查失败原因。由外部因素引起的失败可以重跑，但如果某个依赖更新仍存在无法解释的失败，就不要合并。
4. 如果某个不兼容的更新必须推迟，请把新增的忽略规则限定在受影响的依赖、版本和目录范围内。如果共享的配置条目中只有一个模块需要这条规则，请在添加之前把该模块移到单独的条目中。保留该条目所在的更新分组，使其其他更新仍保持成组。
